# A안: 운영과 백테스트가 같은 뉴스 풀을 쓰도록 — 설계

작성 2026-09-16. 사용자 지시: "장기적으로 해야 할 거면 병렬로 지금부터 시작해." 원칙: 실제 운용에서 가능한 것만, 못 볼 건 학습하지 않는다.

## 문제

- 운영 데몬은 Toss **대시보드 피드**만 본다. 대시보드에는 종목별 기사의 약 16%만 뜨고(09-14 확인), 과거 이력이 없다.
- 그래서 백테스트 표본은 운영 기록이 쌓인 날(하루 약 120쌍)뿐이다. 7일로는 규칙 탐색·밴딧 모두 과최적화로 탈락했다.

## 데이터 양 기준: 밴딧이 가능한 수준

사용자 지시(2026-09-16): 밴딧이 가능할 정도는 되어야 한다. 09-16 매매는 현행 정책(0단계 기준선으로 검증됨)으로 정상 진행하고, 이 작업은 개선이다.

- 목표 표본: **최근 6개월 약 120거래일**(2026-03-16~). 순회 풀 기준 매수 후보 하루 수백 건 → 수만 행.
- 밴딧 준비 완료 판정(모두 충족):
  1. 시간순 폴드(월 단위) 사이에서 고른 λ가 한 칸 이내로 안정
  2. 폴드별 특징 계수 부호가 주요 특징(점수·세션·기사 전 움직임)에서 일관
  3. 최종 확인 20거래일에서 `bayes_judge` 채택 조건 1~3 충족
- 1·2가 안 되면 기간을 12개월로 늘린다(백필 스크립트 `--since` 변경만).

## 목표

운영이 받는 뉴스 풀을 **과거 이력을 받을 수 있는 풀**로 넓혀서, 같은 풀·같은 종목 부여·같은 발견 시각 모형으로 최근 6개월을 백테스트한다.

## 뉴스 풀: 대시보드 ∪ 종목별 순회

1. **대시보드 피드(현행 유지):** 3분 간격. 빠른 반응.
2. **종목별 순회(신규):** 대상 종목 목록을 고정된 순서로 1초에 1회씩 돌며 종목별 뉴스 첫 페이지를 받는다. 새 기사 ID만 판정 대상에 넣는다.
   - 대상 종목: 전일 거래대금 상위 N(기본 600, 장 전 고정). 한 바퀴 약 10분.
   - 순회 순서와 속도가 결정적이므로, 과거 기사의 **운영 발견 시각을 계산할 수 있다**: 발행 후 그 종목 차례가 처음 오는 시각(+ 판정 지연 분포).
3. **관련 종목:** 기사 ID를 여러 종목 목록에서 모아 관련 종목 집합을 만든다(순회 결과 그룹핑). 상세 API의 `companyCodes`와의 일치율을 백필 검증에서 잰다. 불일치가 크면 새 기사만 상세 API 1회 호출로 보완한다(운영·과거 동일 방식).
4. **키:** 운영 키 `uuid5(TOSS_NEWS_NAMESPACE, "toss:" + md5(build_article_url(newsId))[:12])` — 대시보드와 종목별 순회가 같은 기사면 같은 키라 중복 판정하지 않는다.

## 과거 데이터 (진행 중)

- simnode에서 전 종목 × 2026-03-16 이후 종목별 뉴스 백필(`scripts/eval/backfill_toss_company_news.py`, 브랜치 `feat/news-universe`).
- 운영 보호: 요청 간격 ≥ 1초, 평일 08:20~15:45 자동 중단, 429/403 3회 연속이면 정지.
- 대시보드 노출 여부는 과거에 알 수 없으므로, 백테스트 풀은 **종목별 순회 풀만**으로 정의한다(대시보드 전용 기사는 운영에서도 순회 풀과 별도로 표시해 분리 평가).

## 판정 (LLM)

- 운영: 새 (기사, 종목) 쌍마다 `score_article` v2 1회. 순회 풀로 하루 쌍 수가 약 6배 늘어 비용 하루 약 $2(추정). v4 섀도는 끈다.
- 과거: Batch API로 층화 표본부터(1만 쌍 약 $10), 결과가 유망하면 전체(약 10만 쌍 약 $100).

## 백테스트

- 이벤트: 순회 풀 쌍 + 계산된 발견 시각 + v2 판정 → 0단계 리플레이 엔진 그대로.
- 분할: 최근 20거래일 최종 확인(한 번만), 나머지로 LODO/시간순 검증.
- 규칙 탐색과 밴딧을 이 데이터로 다시 돌린다. 채택 기준은 기존 스펙과 같다.

## 운영 반영 순서

1. 백필 + 그룹핑 검증 (진행 중)
2. 운영 폴러에 종목별 순회 추가 — **판정·신호 저장만, 주문은 끔**(dry-run)으로 며칠 운영해 실제 발견 지연과 호출 안정성을 잰다
3. 과거 표본 판정 → 6개월 백테스트 → 채택 정책 결정
4. 순회 풀 주문 활성화

## 위험

- Toss 비공식 API 차단: 속도 제한과 장중 백필 중단으로 완화. 운영 순회(1 req/s)는 차단 시 대시보드 피드로 자동 후퇴해야 한다.
- 순회 풀 확대로 신호가 늘면 동시 보유 한도 경쟁이 달라진다 — 백테스트가 같은 한도로 재현한다.
